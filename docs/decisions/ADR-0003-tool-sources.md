# ADR-0003 · 三工具源统一注册表

> 状态：已接受  
> 日期：2026-11-03  
> 关联：[01-architecture.md](../01-architecture.md)、[ADR-0004](./ADR-0004-tiered-approvals.md)

## 背景

首期同时要求代码注册、目录插件、MCP 三种工具来源。若各自维护一套注册/调用/审批逻辑，会出现三套风险语义、三套命名、三套事件，无法验收。

## 决策

- 所有工具进入一个 `ToolRegistry`，统一：
  - 名称规范化与冲突检测；
  - 风险声明（read / write / exec）；
  - zod 参数校验；
  - 审批包装；
  - 超时、结果截断、事件。
- 来源命名：
  - code：声明名；
  - plugin：`plugin__<plugin>__<tool>`；
  - MCP：`mcp__<server>__<tool>`；
  - 运行时内置：`runtime__<name>`（如 `runtime__spawn_subagent`）。
- code/plugin 工具必须显式声明 risk，缺失即注册失败；MCP 默认 `exec`，只有只读注解才降级为 `read`。
- v1 同一轮多个 tool call **顺序执行**，审批串行；并发优化留待后续。
- 结果统一归一化；错误作为 `ToolMessage` 回给模型，让模型有机会纠正。

## 后果

**正面**：

- 一套审批/事件/命名规则覆盖三种来源，验收可枚举。
- 新工具来源只需适配注册入口，不改主循环。
- 风险默认 fail-safe，避免“忘了声明就自动放行”。

**负面/风险**：

- 命名空间限制较严（安全字符、64 字符），插件/MCP 原名需映射。
- MCP 注解质量参差；默认 exec 会增加审批噪音。
- 顺序执行牺牲部分性能，但换取确定性与审批 UX。

## 备选方案

- **三套独立注册表**：实现快，但审批/事件/命名会分叉，否决。
- **只支持 MCP**：不满足代码注册与目录插件需求。
- **只支持代码注册**：不满足扩展性目标。
- **并行执行 + 并发审批**：v1 UX 与 trace 不确定性过高，推迟。

## 复审条件

- MCP 注解标准普及，默认风险可更精确；
- 顺序执行成为明显瓶颈；
- 需要支持第四种工具来源（如远程 registry）。
