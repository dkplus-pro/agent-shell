# ADR-0008 · 首期范围与交付策略

> 状态：已接受  
> 日期：2026-11-03  
> 关联：[00-requirements.md](../00-requirements.md)、[02-roadmap.md](../02-roadmap.md)

## 背景

最初要求“拆分实现阶段”，后续又明确“首期 = 第一个可运行阶段全含”。两者需要调和：既要一次交付全功能，又要有可执行的实现顺序和验收门禁。

## 决策

- **首期 v0.1 包含全部功能需求**：双 Provider、单 agent、三工具源、分档审批、三子 agent 形态、会话、trace、CLI、参考场景。
- **内部拆 8 个阶段（0–7）**：阶段是执行/验收单位，不是发布单位；每阶段有 demo 与门禁。
- **只有阶段 7 结束才打 `v0.1.0`**；之前不公开发布。
- **单一离线端到端剧本**作为首期验收；live smoke 作为手动补充。
- **不砍功能**：范围变更必须写新 ADR 并更新 00/02；不允许“先不做 MCP/插件/子 agent”。
- 本地 commit 作为检查点；不 push、不发布，除非用户明确确认。

## 后果

**正面**：

- 与用户“首期全含”的选择一致。
- 每阶段有可运行 demo，风险不会全部堆到最后。
- 契约在阶段 0 冻结，避免边做边改。

**负面/风险**：

- 首个正式版本周期长；期间没有对外可用版本。
- 集成风险集中在阶段 5–7；需要严格门禁。
- 三套工具源 + 三种子 agent 的组合测试量大。

## 备选方案

- **增量发布**：更早可用，但与“首期全含”冲突。
- **先最小壳再补齐**：降低早期风险，但用户已明确否决。
- **功能开关**：增加复杂度，且不改变总工作量。

## 复审条件

- 进度严重偏离，需要重新划分发布边界；
- 用户改变“首期全含”的决策；
- 某个能力被证明不可行，需要降级或替换。
